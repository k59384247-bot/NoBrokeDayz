# Data and permissions — Phases 1–3, Phase 4 case lifecycle and Phase 5 Step 1 inspection

## Schema boundaries

- SQL files in `supabase/migrations/` are the schema authority. Local `supabase/config.toml` disables automatic exposure of new public tables; every exposed object needs explicit grants and, for tables, explicit RLS and policies in its migration.
- `public` is the Data API schema. Its `CREATE` privilege is revoked from API roles. `public.job_categories` is public reference data. `public.profiles` contains only ordinary profile fields and is readable/updatable only by its owner; protected identity fields are not columns on this table.
- `app_private` is not in the Data API schema list. `PUBLIC`, `anon`, `authenticated` and `service_role` have no schema privileges. It contains identity, school challenge/ownership, verification submission/evidence/review, staff-grant, suspension, private financial records, audit and outbox records. No direct API-role grants are made on these tables.
- Default table and sequence privileges for `postgres` in `public` are revoked from `PUBLIC`, `anon`, `authenticated` and `service_role`. Future migrations must explicitly grant only intended operations. Do not alter Supabase-managed Auth or Storage schemas here.
- `lib/database.types.ts` is generated from the local database's `public` schema. Regenerate it after each migration; never hand-edit generated definitions.

## Phase 2 Step 7 — manual verification review

Migrations `20261102000400_verification_review_workflow.sql`, `20261102000500_verification_review_invariants.sql` and `20261102000600_verification_review_retry_serialization.sql` add immutable review submission versions, idempotency records, evidence purpose labels, attributable student endorsements, preserved reviewer assignment history and serialized duplicate decision keys. Review decisions are append-only; assignment rows record when their active period ends. The authenticated user commands are `submit_my_verification`, `get_my_verification_history`, and `endorse_partner_verification`; actor identity comes from `auth.uid()`. Review queue, assignment, decision and evidence-download commands are `service_role`-only narrow RPCs, called by the `verification-review` Edge Function after Supabase Auth `/user` validates the bearer and the handler derives the actor from the verified Auth subject. Never accept actor IDs from request JSON.

Student manual fallback requires a student submission and a ready `student_id` evidence item before approval. A student with current allow-listed school proof cannot open the manual route. Partners submit legal name and choose one connection route: a `campus_shop_location` item, `campus_staff_id` item, or verified-student endorsement; each also requires a ready `government_id` item before approval. The endorsement is attributable evidence only. It adds no capability and is checked again against the endorser's current active approved student/work capability at approval time. Partner approval can derive `can_hire` only; it cannot grant `can_work`.

Reviewers need active account status, a current `verification_review` grant, AAL2 from the Auth-validated bearer, and a current assignment to inspect detailed queue data or request file access. Reviewer candidate lists contain only minimal unassigned metadata. Assignment and decision commands lock the submission and compare expected version/state; conflicts return `stale_state`. Idempotency keys prevent retry duplication. Each review decision, submission and assignment is audited; submission/review decisions also create a pending identity notice request in the same transaction. No notice is reported as delivered and no email sender is included. Own-history responses exclude evidence keys, file bytes and other users.

Submissions permit at most three evidence files, each up to 5,000,000 bytes, using JPEG/PNG/PDF; evidence purpose is bound when requesting the upload intent. This maximum is an approved Step 1 verification contract value. Uploads remain quarantined because this local project has no malware scanner or robust PDF/image sanitization. A simulated ready evidence row in transaction-scoped database tests is not evidence that any uploaded file is safe and is not exposed as a client command. Approval therefore remains unavailable for real uploaded documents until the separate scanner/safety gate is passed.

## Phase 2 Step 8 permissions

The `identity-staff` handler validates bearer tokens through Auth `/user`, then derives actor ID and AAL from the verified token. The browser cannot supply actor, AAL, staff or capability values. The service executor can call only named public RPCs and still has no private-schema access. Database functions recheck current AAL2, active account and the required unrevoked grant for every protected command. Detailed review records additionally require the actor's current assignment. AAL2 without the right grant, or a grant without AAL2, is denied.

`public.profiles` policies check current account status on every own-row select/update. Suspension blocks direct Data API profile access using already-issued tokens. `get_my_identity_help_context()` returns only the caller's own suspension state and remains available while suspended. Suspension and unsuspension append reasoned history/audit and preserve profile, evidence and review records. Staff grants cannot be read or changed by browser roles; grant insert/revoke events append audit records, and grant rows cannot be rewritten or deleted. The synthetic bootstrap and TOTP evidence are documented in [staff-access.md](staff-access.md). Reserved dispute/money capabilities have no implemented workflow or finalization command.

The SQL tests verify user ownership, current grant/AAL2/assignment checks, needs-information, stale decisions, idempotent retries, append-only history and notice requests. The Edge boundary tests verify that actor IDs cannot be supplied by clients. The queue is queried directly from committed database state (no Realtime/UI claim); a separately timed, committed-submission-to-reviewer-query acceptance measurement remains to be captured before claiming the ≤60 second operational target.

## Phase 4 Step 4 case investigation and evidence

Case investigation records, requests, responses, contact logs, fact notes, non-response assessments, staff notes, upload intents, file metadata and file-access audit records remain in `app_private`; clients and the generic service role have no direct table access. Public server RPC wrappers are service-role-only. `case-command`, `case-read` and `case-evidence` derive the actor from verified Auth and ask the database to recheck current role/grant, assurance level, case assignment and participant scope.

Active and suspended assignment parties may read their own safe case overview and answer only requests addressed to them. The participant view filters requests/replies by role and files by owner; it omits private notes, contact records, staff identities, object keys, hashes and unsafe bytes. The assigned reviewer requires an active account, current `dispute_review`, AAL2 and exact current case assignment. A senior non-response signoff requires a separate active `case_senior_signoff` grant, AAL2, a current contact-set hash, a different person from the assigned reviewer and no party conflict. That grant does not provide reviewer-detail or evidence-byte access.

Case file metadata is separate from identity verification metadata and grants. `case_file_policy` defaults to five files and 5,000,000 bytes per case file; both limits are configurable within a technical ceiling of 25 files and 100,000,000 bytes each. Identity verification remains capped at three files. Uploads use private `case-evidence-quarantine`; browser roles cannot read or write that bucket. The handler verifies bounded size and file signature, but the project has no malware scanner, PDF sanitizer or image re-encoder, so each actual uploaded file is stored as `quarantined` and cannot be downloaded by staff or participants. No command promotes an upload. The only ready-file path is an explicitly marked `synthetic_test` row in isolated tests.

Case overview/metadata reads write case/file access audit records. Byte download is a separate request with a fresh reviewer assignment, grant and AAL2 check, followed by a separate byte-access audit. No Storage URL is returned. Interrupted upload objects remain private; do not infer a cleanup or statutory retention period until a reviewed policy exists. See the case contract's command-by-command DB/handler/Edge acceptance map for exact test boundaries.

## Phase 4 Step 5 — decision proposals and approvals

`case-command` accepts `propose_case_decision`, `approve_case_decision` and `signoff_decision_nonresponse`. Each calls a named `service_role`-only wrapper; `app_private` remains inaccessible to client roles. The database derives the actor from the Auth-validated Edge request and rechecks active account, AAL2, current grants, case scope and party conflicts. Financial approvers must also have trusted admin-controlled Auth app metadata `staff_principal_kind=human`; user-editable metadata and service/unknown principals do not qualify.

The assigned proposer needs both `dispute_review` and `financial_approve` and creates approval record one. A different qualified person creates record two. All four outcomes conserve the exact allocation gross; commission is 5% half-up on worker-awarded gross only. Changed amounts, recipient, reason or evidence basis requires a new version and new approvals. Non-response signoff is a separate senior record tied to that same version and excludes the parties, assigned reviewer and proposer. `financial_inspect` stays read-only.

The reviewer may read the decision after approval. Participant responses continue to show a safe pre-decision stage and no decision details until Step 6 durably notifies both parties. Step 5 creates no journal entry, hold release, award, refund payable, external payment or appeal clock; those remain for later manual finalization and settlement steps.

### Messages and access

Migration 20261104000500_application_messages.sql stores application messages and per-reader/thread cursors in app_private. Messages and thread identity are immutable. A participant's sender-scoped client UUID prevents duplicates; same-ID/same-body replay returns the saved message, while changed content conflicts. The database assigns a stable bigint sequence. The read query supports after_sequence; the Edge projection exposes at most 50 rows and a decimal-string next_after_sequence.

The poster and applicant are derived from the application and job, not request-supplied actor fields. The database rechecks their current role capability. Sending is limited to applied or accepted applications; rejected/withdrawn/closed history remains read-only. Read cursors only move forward and cannot exceed the thread's last saved sequence.

Case staff receive the thread snapshot only through the current assigned-reviewer case projection, bounded to messages through the case-open sequence. It is not a direct thread grant. Case detail requires the active reviewer assignment, current dispute-review grant, AAL2 and non-party status. The financial-inspection capability does not grant case access. No Realtime authorization policy, private Broadcast topic, or client channel exists, so the existing actor checks are not socket evidence.

### Notices and delivery records

In-app notice reads are recipient-scoped through notifications-read. The response currently contains safe notification type/title/time/read-state fields and no typed destination. Database uniqueness prevents duplicate recipient/event/type notices. A notice can only be marked read by its recipient.

Marketplace outbox rows are immutable source events; they do not have a delivery state or consumer. Identity and financial outboxes have delivery-state fields but no general email/notice worker, claim lease, reclaim, retry/backoff consumer or provider reconciliation path. Payment-operation jobs are durable and leased for the local fake payment adapter; they do not deliver notifications. No Zoho or ordinary email sender is implemented. In-app read state is separate from outbound delivery state.

Destination IDs, when later added, must be typed and allow-listed. Opening an application/thread, assignment, case or wallet item must call its owning read path and recheck current actor, scope, account status, current grant/AAL2 and participant/ownership rules. An arbitrary URL or client-provided authorization claim is not a destination contract.

### Profile and review boundary

The current safe profile projection returns worker_rating and poster_rating as null and both review counts as zero. Generic profile update rejects protected counters. completed_work_count is computed from assignments with the subject as worker and work_state='completed'; there is no separate poster completion count or review projection. No review table, review report, moderation record or rebuild command exists. The future eligible-completion rule must account for ordinary poster-confirmed completion and eligible finalized worker awards, while no-action and refund-only outcomes do not by themselves count as completion.

### Staff operations and missing permissions

Identity review, case/appeal handling, and financial trace/reconciliation already have separate server handlers and narrow DB grants. Case investigation remains case-scoped. Financial trace/reconciliation requires current AAL2 financial-inspect authority and is read-only. No marketplace metric read, review-moderation permission, notification delivery exception queue or delivery-replay command exists. Any future moderation/metrics/delivery operations need explicit least-privilege capabilities and database-boundary tests; UI visibility or an owner-only query is not permission proof.

The current command-to-evidence map and exact future test boundaries are recorded in [phase-5-evidence.md](phase-5-evidence.md). Existing local message, notice and case evidence does not establish Realtime revocation, email delivery, reminder scheduling, review eligibility/moderation, review counter rebuilding or metrics correctness.
