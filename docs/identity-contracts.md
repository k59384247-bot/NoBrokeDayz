Status: **approved for Phase 2 implementation on 30 October 2026**. The owner approved all five decision groups as written. This contract records the resulting identity rules and implementation boundaries. The approved baseline remains `spec.md`, `docs/product.md` (F1/F2) and `docs/technical.md` (identity/security); any conflict still requires an explicit decision.

Use the pinned native local Supabase stack, synthetic accounts, synthetic evidence and reserved `.test` school domains (for example, a test fixture such as `student@unilag.school.test`; this is deliberately not a real institutional domain). Step 4 adds the existing-account phone-change path and private phone binding; real native Auth-to-signed-HTTP-hook delivery is locally verified with synthetic capture. The UNILAG institutional domain allow-list remains a live gate: actual domains remain unconfirmed. Local `.test` values exercise exact matching only and must never be copied into production configuration.

## Phase 2 Step 5: supplementary school email

School email is separate from the Supabase login email. The `identity-school-email` server command verifies the caller's bearer through Supabase Auth `/user`, derives the actor from that response, generates a cryptographically random six-digit code, computes an HMAC-SHA-256 digest using a server-held secret, and sends the code only through the configured email adapter. It never updates `auth.users.email`, creates another Auth user, or accepts a caller-provided actor ID or digest.

The digest and challenge state live in `app_private.school_email_challenges`; normal browser roles and `service_role` cannot read that table. Narrow `service_role`-only RPC gateways execute the issue, confirm and delivery-failure transactions. The server secret stays outside the database and is not committed. Local secret files are held under ignored `.supabase-home/` with owner-only permissions. The digest-key version is recorded with each digest and currently uses key version 1. Rotation and overlap with old keys are not implemented; hosted secret provisioning and rotation remain launch gates.

The local allow-list contains `school.test` only through `supabase/seed.sql`. It is not inserted by a migration and is therefore not present in a hosted database by applying migrations. The database lowercases and trims the address, checks exact domain equality, and rejects suffix lookalikes such as `school.test.attacker.test`. A login address cannot be reused as the supplementary address. The actual UNILAG domain remains unconfirmed and must be explicitly configured after verification.

| Challenge control | Enforced behavior                                                                                                                                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Code and storage  | CSPRNG six-digit code; only a 32-byte keyed digest stored at rest; no code in API response, logs or browser-readable table                                                                                               |
| Expiry            | 10 minutes, checked in the confirmation transaction                                                                                                                                                                      |
| Resend and retry  | 60 seconds per account/address; a new actor-scoped idempotency key creates a resend and invalidates the prior open challenge. Retrying the same key returns the prior challenge state/reference without another delivery |
| Issuance caps     | Five per account/address in a rolling hour; ten per account/address in a rolling 24 hours; serialized and counted in PostgreSQL                                                                                          |
| Invalid attempts  | Five wrong codes per challenge; row-locked counter, and the fifth failure invalidates it                                                                                                                                 |
| Consumption       | Challenge is bound to Auth user ID, normalized address and version; successful confirmation consumes it in the same transaction                                                                                          |
| Address ownership | One active owner per normalized address and one active address per user; a uniqueness race has one winner and the losing response does not identify the owner                                                            |
| Delivery failure  | The just-issued challenge is invalidated; safe generic 503 response; delivery acceptance alone does not create ownership                                                                                                 |

The email adapter contract sends a `to` address, the `institutional-email-ownership` template name and `code`/`expires_minutes` variables. Local checks use an authenticated loopback capture adapter that keeps synthetic messages in process memory. This envelope is suitable for a later Zoho adapter, but no Zoho account, school mailbox, or real email delivery has been configured or tested. Supabase login confirmation, password recovery, and Auth email templates/hooks are separate and do not create supplementary school ownership.

Confirmation creates current school ownership and audit/outbox history atomically. A successfully verified replacement revokes the prior address, invalidates that account's other open school challenges and revokes any stale school-route capability rows before re-deriving eligibility. A competing owner is checked before this replacement, and address-scoped advisory locking plus unique indexes ensure that a race has one owner without disclosing its identity. Track A qualification is attempted in that same transaction and only succeeds for a student with confirmed login email, affirmative age confirmation, current Auth-matched phone proof, current allow-listed school ownership, and active account status. The system grants exactly `can_hire` and `can_work` for this school route; Track B remains separate. If phone or age is missing, the address can be verified but capabilities remain empty. If the account is suspended, verification can complete but the suspension stays in effect and no capabilities are granted. Auth phone/login-email updates trigger a fresh eligibility check, and own-status projects effective capabilities only while current Auth and protected facts still agree.

`npm run check:school-email` runs 181 current pgTAP assertions plus its boundary and local Auth/database integration suites, including idempotent issue retries, challenge replay, exact domain matching, five-attempt lockout, competing owners, parallel consumption, suspension and automatic qualification. It resets only the local database before and after testing; see [runbook](runbook.md). No hosted services, real email or identity document are involved.

## Phase 2 Step 6: private evidence files

The `verification-evidence` server command requires a verified existing Auth session and an owned pending submission. It creates a five-minute, one-use upload token bound to the user, submission, position, MIME type and size. The token is stored as a digest. The server generates the object key and streams the file through its private Storage credential; browser roles have no direct Storage permission. This server-mediated upload avoids Supabase signed upload links, which are currently valid for two hours. The approved five-minute upload-access limit remains in force.

Both evidence buckets are private. The quarantine bucket accepts at most 5,000,000 bytes and only JPEG, PNG or PDF content types. The handler checks actual body length, content signature, safe key binding and stored-byte SHA-256 after readback. It uses insert-only storage and UUID-derived paths. Evidence count is three per verification submission; the five-file limit is only for dispute evidence.

The handler checks basic image/PDF signatures and rejects common PDF active-content markers. This is not malware scanning, full document parsing or safe re-encoding. Every accepted upload therefore remains `quarantined`; no evidence can reach reviewers or support an approval yet. The local one-pixel PNG and one-page PDF are synthetic fixtures only. The real-document gate stays closed until a scanner/sanitizer is available and tested.

The reviewer URL command requires a verified AAL2 token, current active account, current `verification_review` grant and a `ready` evidence record. It sets the approved 10-minute URL lifetime and requests an attachment response. Signed URLs are bearer access until expiry; changing a grant does not revoke an issued URL. Because no scanner can create `ready` evidence, local application-level reviewer delivery remains unavailable. Local Storage tests use a test-only synthetic object to prove attachment headers and expiry independently.

The append-only private access log records upload intent issue/claim, rejection, quarantine finalization and allowed/denied reviewer-link requests. `npm run cleanup:verification-orphans` is local-only and deletes only unreferenced quarantine objects older than 24 hours; finalized metadata and private review history are excluded. This cleanup delay is not a legal document-retention rule. See [verification-files.md](verification-files.md) and [runbook.md](runbook.md).

## Approved code and throttling policy

### Supabase Auth phone OTP

Supabase Auth generates and verifies the phone-change OTP. The Send SMS Hook only delivers it. The flow updates `phone` on the signed-in existing Auth user and verifies with the phone-change type; it must not use a phone signup/sign-in path. Bind resulting phone proof to the same `auth.users.id`.

| Control                                |                                                                                         Proposal | Enforced by                                                                                                                                                                  |
| -------------------------------------- | -----------------------------------------------------------------------------------------------: | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Phone OTP lifetime                     |                                                                                    **5 minutes** | Configured locally as `auth.sms.otp_expiry = 300`; actual Auth-generated OTP rejection after 300 seconds is verified through the signed local delivery path                  |
| Minimum resend interval                |                                                               **60 seconds per Auth user/phone** | Configured locally as `auth.sms.max_frequency = "60s"`; Supabase Auth applies it                                                                                             |
| Auth endpoint request/verify throttles |         Local `token_verifications = 5` quota per 5 minutes per IP, with platform burst behavior | Supabase Auth; IP-scoped verification throttling is not a per-challenge counter                                                                                              |
| Application per-phone send cap         |                 **5 sends per phone per rolling hour** and **10 per phone per rolling 24 hours** | Local synthetic capture adapter enforces in-memory caps on actual hook delivery. Durable cross-instance enforcement remains a live gate                                      |
| Verification attempts                  | **5 invalid attempts per challenge**; challenge then requires a new OTP subject to resend limits | Approved product threshold, but local Supabase control is only IP-scoped. Do not claim exact per-challenge enforcement until an unbypassable supported boundary is available |

Supabase documents the phone-change flow as `updateUser({ phone })` followed by `verifyOtp({ phone, token, type: "phone_change" })`. The local check uses actual Auth-generated OTPs and signed Standard Webhooks requests; it does not configure fixed test OTPs. The handler validates signature and timestamp before passing the code to synthetic-only loopback capture. In the pinned hook payload, `sms.phone` is the requested destination; `user.phone` may still contain the previous number. Auth stores phone digits without `+`; only the protected application mirror and command projection add that prefix. See [phone change](https://supabase.com/docs/guides/auth/phone-login), [Send SMS Hook](https://supabase.com/docs/guides/auth/auth-hooks/send-sms-hook), and the [pinned payload definition](https://github.com/supabase/auth/blob/v2.197.0/internal/hooks/v0hooks/v0hooks.go). Hosted configuration, provider delivery, and the remaining abuse-control gates require later evidence.

### Supplementary school challenge

This is an Identity-owned challenge, separate from Supabase login-email confirmation/recovery. It binds actor, exact normalized school address, challenge version and expiry; stores only a keyed digest; and is consumed once atomically. Approved values:

| Control                  |                                                                                 Approved value | Enforced by                                                  |
| ------------------------ | ---------------------------------------------------------------------------------------------: | ------------------------------------------------------------ |
| Code                     |           Cryptographically random 6-digit numeric code; keyed digest, never plaintext at rest | Identity challenge command/database                          |
| Expiry                   |                                                                                 **10 minutes** | Identity challenge row and confirmation command              |
| Resend wait              |                                                    **60 seconds** for the same account/address | Identity command/database                                    |
| Issuance cap             | **5 challenges per account/address per rolling hour**, **10 per account per rolling 24 hours** | Identity command/database; delivery adapter is not authority |
| Invalid confirmation cap |                               **5 attempts per challenge**; consume/lock challenge after limit | Atomic Identity command/database                             |
| Reuse/replay             |                                              One successful consumption; all later uses denied | Atomic Identity command/database                             |

Supabase Auth email OTP expiry controls login confirmation/recovery, not this school challenge. The approved school-code expiry, per-address ownership uniqueness and one-use semantics are supplementary app rules; configuring Supabase Auth alone cannot enforce them.

## Existing-account ownership and contact changes

Registration creates one Supabase Auth user with a personal login email/password. The selected account type and age affirmation are submitted to a narrow onboarding command and recorded in protected Identity data, keyed by the Auth user ID. Auth user metadata may contain cosmetic hints only; it is never authoritative for type, approval, capabilities, suspension or staff grants. Repeated signup/provisioning for the same authenticated identity is idempotent and cannot create another application identity row or switch type.

To bind a phone, an authenticated user starts the supported phone-change flow on their existing Auth user. `lib/auth/phone-change.mjs` requires a current Supabase Auth user with confirmed login email, normalizes Nigerian local/country/E.164 forms, sends `updateUser({ phone })`, and confirms only through the `phone_change` OTP type. It returns a pending marker or a narrow confirmation projection and safe error categories; it never returns OTPs or raw Auth error text. Phone-only signup is disabled. Only Auth's successful confirmation of that change triggers the mirrored current phone proof. A phone change immediately deletes the previous mirror until the new number is confirmed. If a number is already owned or pending for another account, fail safely without disclosing the other account. Resolve duplicates through a private support/review route; never merge Auth users or move verification history automatically. A database trigger serializes claims and ensures one active/pending owner at a time.

Approved invalidation/reconciliation behavior:

| Change or Auth event                              | Invalidation and reconciliation                                                                                                                                                                                                                                                                |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Login email changed                               | Supabase's current confirmed email becomes the login-email fact only after Auth confirms it. Require recent authentication for the change. School proof and phone proof are separate and do not transfer to the new login address. A changed login email alone does not revoke track approval. |
| Login email confirmation/recovery                 | Updates Auth login ownership only. Never creates or restores student/partner approval, age confirmation, phone proof, capabilities or staff grants. Recovery does not bypass suspension.                                                                                                       |
| Phone change requested                            | Mark current phone proof unavailable as soon as Auth reports a pending/new phone change; suspend capabilities requiring the shared phone prerequisite until the new phone is confirmed. Do not treat delivery, OTP request or hook success as proof.                                           |
| Phone change confirmed                            | Reconcile current Auth phone and verified state to the same account ID. Restore eligibility only if age, track approval and all other facts still pass and account is not suspended.                                                                                                           |
| Institutional email replaced or ownership removed | Revoke that school-email ownership proof, cancel outstanding challenges and remove Track A qualification if that address was its active proof. An independently approved student-ID fallback remains its own approval method. Never transfer the old proof to a replacement address.           |
| User type correction                              | No self-service change. A correction is a scoped staff command with a reason, fresh review of the destination track, and an append-only audit event. Until resolved, keep the stricter capability set.                                                                                         |
| Suspension / unsuspension                         | Current protected status overrides every older JWT/UI claim. Suspension removes ordinary capabilities immediately after commit; unsuspension is explicit, reasoned and authorized and does not invent missing/expired proofs.                                                                  |
| Staff grant/revocation                            | Current protected grant and required MFA are checked at every staff command/read; metadata, JWT role strings and cached capability lists cannot preserve revoked access.                                                                                                                       |

Identity commands must reconcile Auth facts from a trusted Auth lookup/event path, not caller JSON. If Auth and the protected mirror disagree or are temporarily unavailable, fail closed for the dependent capability and expose a safe pending/reconciliation state. Keep login email, school address and phone separate in every response. Existing access tokens need not be claimed instantly revoked by Supabase; sensitive commands query current protected status and current required Auth facts.

## Safe command contracts and approved transitions

All commands derive actor ID from a validated Auth access token. Never accept an actor ID, user type, approval, capability, suspension state, MFA assurance or staff grant as authority from request JSON. Use schemas with unknown-field rejection, stable safe error categories, correlation IDs and idempotency keys where noted. Responses are explicit projections, never complete private rows.

### Phase 2 Step 9 profile command implementation

`profile-command` is a local/backend command boundary, not a profile page or discovery feature. It accepts only `POST` JSON actions `update` and `view`, allows at most 8 KiB per request, rejects unknown keys, checks the bearer with Supabase Auth `/user`, and derives the actor from that verified user. Responses are `no-store`, include `x-request-id` and `request_id`, and return stable categories (`authentication_required`, `invalid_profile`, `profile_access_denied`, `profile_not_found`, `profile_service_unavailable`) without database details.

`public.profiles` remains owner-readable through RLS, including during unverified onboarding while active. Generic authenticated table updates are revoked. The profile Edge Function calls the `service_role`-only `server_update_profile_for_actor` and `server_get_safe_profile_for_viewer` RPCs; these gateways alone can invoke their private helpers. The service role has no `app_private` usage or table access. A current suspended account cannot update, even with an older valid session token.

The own-status command reports current `verified`, `can_post` and `can_work` booleans. `can_post` represents the existing protected `can_hire` capability. These booleans are recomputed from current login-email confirmation, current Auth phone plus its same-user verified binding, age affirmation, active account and approved track. Track A email approval additionally needs a current allow-listed institutional-email ownership; Track A fallback uses its approved review; Track B partner gets `can_post` only. A stale/missing capability row cannot bypass these checks; suspension overrides them.

The `view` action accepts only a target profile UUID. Both viewer and target need current non-empty capabilities; guessed, missing, unverified and suspended targets return the same not-found category. The projection explicitly contains ordinary profile display fields, system-owned account type/badge, ratings as `null`, rating counts `0`, and completed work `0`. It omits login/institutional email, phone, legal identity, bank data, evidence, capabilities, staff grants and private status reasons. This does not enable anonymous discovery or create a marketplace feature.
