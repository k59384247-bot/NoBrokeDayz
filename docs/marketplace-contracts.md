# Marketplace command and state contracts — approved model, Phase 3 local closeout

Status: Phase 3 Steps 4–10 have local synthetic implementation/test evidence. Specific command-level Edge coverage gaps and all live-service gates are recorded in [phase-3-milestone.md](phase-3-milestone.md). Financial inspection is read-only and restricted to local/test configuration.
Prepared: 4 November 2026.

This document defines the backend contract for the locally simulated Phase 3 path. On 3 November 2026 the owner approved the listed field bounds for local validation only; they are not live exposure limits. Current database migrations remain the schema source of truth.

## Current repository boundary

The public schema contains `public.job_categories` and ordinary `public.profiles`; job, terms, finance, applications, assignments, holds, threads, messages, notices and outbox records live under `app_private`. Step 4 adds private jobs, immutable terms and funding; Step 5 adds bounded discovery/detail and owner history; Step 6 adds applications, one assignment per accepted application and one private message thread per application; Step 7 adds participant work progress, ordinary poster-confirmed release and an unresolved participant hold; Step 8 adds private wallet projections, versioned synthetic destinations and durable simulated withdrawals; Step 9 adds recipient-only notice reads, scoped financial tracing and reconciliation. `marketplace-command`/`marketplace-read`, `wallet-command`/`wallet-read`, `notifications-read` and `ops-financial-inspection` expose the respective scopes. A funded three-slot job has three allocations, and after three acceptances it has three assignments bound one-to-one. Neither private rows nor internal finance helpers are directly available to API roles. Enabled categories are resolved from controlled slugs: `errands`, `tutoring`, `design-creative`, `writing-editing`, `tech-help`, `event-support`, and `other-permitted-campus-services`. Generated public database types remain public-schema-only.

All Edge handlers validate the bearer with Supabase Auth `/user`, derive the actor from that subject and call narrowly scoped `service_role`-only RPCs. They accept action-specific JSON allow-lists; the service role has no direct `app_private` schema access. SQL rechecks current capability and suspension for protected writes and discovery/detail. Owner history and wallet status are separate owner-scoped reads; suspended approved users retain only safe own financial status. Assignment status remains a participant-only read after suspension. Funding persists its immutable operation and intent before the local fake-adapter boundary; only the leased runner's authoritative lookup can complete funding. Wallet/destination changes and withdrawals are locked to local simulator configuration. `ops-financial-inspection` also requires an AAL2 session and a current active `financial_inspect` grant at the SQL boundary; it has no mutation action and the Edge entrypoint refuses non-simulator configuration.

Every request derives the actor from the validated Auth token. Request JSON never supplies an authoritative actor ID, role, verification state, capability, suspension status, or staff grant. Each protected write rechecks current account status and current Identity capability facts in the command transaction, so a stale token cannot retain access after suspension or a qualification change.

## Separate objects and states

An application is not a reserved slot. A funded slot owns one principal allocation. Acceptance binds exactly one pending application, one assignment, and one unassigned allocation in a single transaction. A three-slot job therefore has three distinct allocation records and can have three distinct assignments and work states. No worker status is stored on the parent job.

**Listing state** describes discovery and slot availability:

| State              | Meaning                                                                                                                                                                                |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `draft`            | Poster may edit terms; no successful funding and no pending/unknown funding intent exists. Prior authoritative failed/cancelled attempts may remain in history.                        |
| `awaiting_payment` | A server-created exact-total funding attempt exists; terms and request fingerprint are fixed while its outcome is pending or unknown.                                                  |
| `open`             | Exact funding is verified, at least one allocation remains unassigned, and applications are being accepted.                                                                            |
| `filled`           | No unassigned allocation remains. Assignments can still be in different work states.                                                                                                   |
| `expired`          | Application deadline has closed discovery and new applications. Funded unassigned principal remains held; the poster may still accept a valid application submitted before the cutoff. |
| `cancelled`        | Reserved for an explicit later cancellation/refund workflow; not a Phase 3 command.                                                                                                    |

Derive `filled` when no allocation remains unassigned, even if the deadline later passes. Otherwise derive `expired` once the deadline is reached; derive `open` only while at least one allocation is unassigned and intake remains open. This keeps a fully accepted job filled while its assignments progress independently.

**Assignment work state** is independent: `assigned → in_progress → submitted → completed`, with `cancelled` reserved for a later explicit workflow. A dispute/safety hold is a separate status dimension and preserves the prior work state. `hold` freezes only the matching assignment's unresolved allocation. It does not mark the assignment completed or cancelled, move cash, release earnings or authorize a refund; an internal balanced ledger reclassification may label that allocation dispute-held.

**Application state** is `applied`, `accepted`, `rejected`, `withdrawn` or `closed`. A student can apply once per job; a unique application/job/worker key prevents reapplication after withdrawal or rejection. The poster can accept or reject only an `applied` application; its worker can withdraw only while it is `applied`. Rejected and withdrawn threads remain readable by their two participants but cannot receive messages. `closed` is reserved for a later closure command and cannot be set through the Step 6 HTTP actions. Cancellation and appeal outcomes remain disabled.

All timestamps are UTC `timestamptz`, created by the server. Use one database clock for deadline checks. Application deadline and work `needed_by_at` remain different fields. The existing approved rule requires `application_deadline_at <= needed_by_at`; crossing either timestamp never releases or refunds funds. The work-needed time does not automatically cancel, complete, or block a valid assignment from starting/submitting late.

## Immutable terms and allocation binding

Each draft has a numbered terms version. The funding intent snapshots the exact terms version, currency, `gross_per_worker_kobo`, slot count and computed total. No terms may change while the attempt is pending or unknown. Once authoritative terminal failure/cancellation proves no funds were collected and no success is still possible, the unfunded job may return to `draft`; prior terms and attempts stay immutable, and an edit creates a new terms version. A mismatch remains an ops exception, not a failed attempt that can be silently retried. After exact funding succeeds, scope, price, category, location, slot count and funded principal are immutable. A material change requires a later replacement/cancellation path; it cannot overwrite a funded version or accepted assignment.

An authorized application-deadline extension for still-unassigned slots must create a new prospective terms version. It cannot rewrite an accepted assignment's snapshot. No deadline-extension command is in the Phase 3 Step 1–10 user journey; its treatment of already-pending applications must be contracted before that later command is implemented.

Successful exact funding creates one allocation per slot, each for one worker's gross amount. Allocations start unassigned. Acceptance locks the job and candidate allocation, then creates one assignment and changes that allocation's current binding to the selected assignment. The allocation pointer and a separate immutable history boundary allow one current assignment while retaining older cancelled assignments. The unique `(job_id,worker_id)` application rule remains. An application alone neither reserves a slot nor decreases `remaining_slots`.

Step 4, 6 and 8 business writes that accept an idempotency key scope it to the verified actor and command and persist a canonical request fingerprint. Identical retries return the original safe projection; altered input with the same key returns `idempotency_conflict`. Step-up proofs are separate one-use credentials and are consumed in the same transaction as their authorized change/reservation. Read commands do not accept a client actor or page size. All routes validate JSON content type, action schema and bounded bodies; responses are `no-store` with a request/correlation ID. Kobo amounts and message sequence numbers are decimal integer strings. Errors use `{"request_id":"…","error":{"code":"…","message":"…"}}`.

Discovery filters combine title/description keyword, location-detail full-text match plus location type, enabled category slug, per-worker gross range (`min_gross_kobo`/`max_gross_kobo`) and needed-by range. Sort newest-first by `(created_at, job_id)` using keyset pagination and a fixed 20-item page; the server fetches one extra row to decide whether to return a next cursor. The base64url cursor carries a version, sort position and normalized filter state; it is only a pagination marker, never authorization. Changed filters reject the old cursor, and SQL rechecks current capability and listing eligibility on every page. The response returns normalized filters and the cursor so a later frontend can restore query state. No exact counts or per-card profile requests are returned. `marketplace-read` uses PostgreSQL full-text search and targeted job/capacity/search/filter indexes from migration `20261104000300_marketplace_discovery.sql`.

The MVP campus ID is a fixed server/database setting; it is not a user-submitted location and the public response makes no claim that an individual has been verified at a physical campus. `public.job_categories` remains readable independently of jobs. Direct Data API job reads and direct browser RPC execution remain denied.

## Listing and assignment expiry behavior

The approved baseline says expiry removes a listing from discovery and does not refund it. The approved server rule is `now >= application_deadline_at` closes new discovery/application requests, with a single database clock and no client-time authority. Existing funded allocations remain held. A timer, reminder, cron, stale browser return or absent response never releases, refunds, cancels or completes money.

The owner approved that the poster may accept a valid application submitted before the deadline after discovery closes, while funded unassigned principal remains. Accepted assignments continue independently past both timestamps; late work can still be submitted and confirmed or held through an authorized participant command. Passing `needed_by_at` alone changes no assignment or ledger state.

## Messaging and notification boundary

Application creation and private thread creation are one database transaction. Acceptance retains that thread. Only the poster and that applicant may read it. Rejected/withdrawn threads remain read-only; `closed` is reserved for later closure behavior. Messages are saved with a sender-scoped client UUID before acknowledgement, receive a unique thread sequence, and are immutable. Reusing a client UUID with the same thread/body returns the saved message; changing either conflicts. Read cursors only move forward and cannot exceed the stored thread sequence. No attachment, general chat, realtime or presence capability is implemented.

Business transactions append the relevant domain event and durable outbox request in the same commit. In-app notice is durable and independent of Zoho email success. Essential events include application, acceptance, submission, completion release, hold, withdrawal state and failure/unknown notification. 24/48-hour reminders and the 72-hour dispute prompt may prompt human action only; they are suppressed when confirmed/held and cannot authorize any money movement. Avoid email for every message.

## Safe HTTP result and error shapes

For new Phase 3 handlers, use one explicit envelope:

```json
{
  "request_id": "uuid",
  "replayed": false,
  "data": {
    "amount_kobo": "285000"
  }
}
```

Every kobo amount is a base-10 integer string with no decimal point, grouping or exponent. `"285000"` means ₦2,850.00. Serialize UUIDs as strings and timestamps as UTC RFC 3339. Error envelope: `{"request_id":"uuid","error":{"code":"stale_state","message":"This item changed. Refresh and try again."}}`. Stable public codes include `authentication_required`, `verification_required`, `permission_denied`, `not_found`, `invalid_request`, `stale_state`, `slot_unavailable`, `payment_pending`, `insufficient_available_balance`, `confirmation_required`, `provider_unknown`, `rate_limited` and `service_unavailable`. Never return SQL diagnostics, raw provider bodies, full bank details, private profile facts or staff notes.

The Step 4–9 marketplace, wallet, notices and ops handlers use bounded action-specific input, explicit safe projections, `no-store` headers and request IDs. Monetary amounts and 64-bit message sequences are decimal strings. A repeated keyed command returns its original result; altered input with that key conflicts. Assignment transition stages are server timestamped. Participant report fields are limited locally to a 2,000-character narrative and 500-character requested outcome, with a controlled report-reason list. These bounds do not add product outcome policy. A held allocation remains held until a future Phase 4 resolution command is approved and implemented. Payment actions and reconciliation use only the local simulator contract. The financial audit hash chain is a local integrity check, not an independent signed checkpoint. The financial outbox has no external email/SMS sender; durable in-app notices are available independently of transport delivery.

## Explicitly disabled in Phase 3

No automatic release/refund, job cancellation, accepted-assignment cancellation, abandonment/reopen, refund, partial award, case decision, appeal, admin financial finalization, two-person approval, reversal debit to worker, ratings, or real Bachs operation is enabled by this contract. `hold` only freezes/reclassifies the affected allocation and records a participant report for later human handling. Beta admin money outcomes remain gated by two independent human approvals bound to an immutable decision version when that later workflow is designed.

Phase 4 Step 1 planning does not change this Phase 3 command contract. The proposed lifecycle, owner choices and command-by-command acceptance plan for evolving immutable reports into resolvable cases are in [case-and-cancellation-contracts.md](case-and-cancellation-contracts.md); approval and no-action accounting interpretations remain pending.
