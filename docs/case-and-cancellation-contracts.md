## Terms and current baseline

- **Report**: the participant's immutable submission that opens a case and freezes one funded allocation.
- **Active case/hold**: the current unresolved case state that blocks work/confirmation/finalization on that allocation. A historical report is not, by itself, an active hold.
- **Decision version**: an immutable proposed outcome, reason, amount split, evidence/terms snapshot and hash. Any material change creates another version.
- **Refund payable**: an authorized obligation to return poster principal. It is not a completed refund, a poster wallet top-up or proof of bank receipt.
- **Voluntary cancellation**: an eligible poster action or matching participant consent, authorized by the parties. It is not an admin dispute decision and does not create a fictitious case.

Phase 3 stores `app_private.assignment_holds` as immutable rows whose `status` can only be `open`. The participant report and the assignment's `prior_work_state` are retained. The hold command moves only that allocation from `assigned` to `dispute_held`, preserving the assignment work state, and appends a balanced internal liability reclassification. It does not release earnings or create a refund. Existing local evidence proves this open/confirm race and safe participant status for the unresolved Phase 3 case; it does not prove resolution or appeals.

Resolution therefore needs an explicit current lifecycle/projection separate from the immutable report. Do not update/delete the report, infer that an old `open` row still blocks forever, or simply change its status constraint. The effective active case must be derived from a controlled lifecycle record and checked together with the allocation state at each write boundary.

## Proposed case lifecycle and outcomes

Use the approved public stages `Open → Under review → Contacting other party → Verifying → Decision made → Appeal (when timely appeal exists) → Closed`. Stage changes are explicit, attributable, idempotent and audited; clocks and failed contact attempts cannot move a case into a money outcome. One active case may cover an allocation. Preserve every prior report and resolution. A later report on the same allocation is allowed only when there is no active case, the assignment is still in an eligible state (`assigned`, `in_progress` or `submitted`), and the caller is an assignment party. A retry with the same key returns the original case; a new case requires a materially new event or evidence, not the same allegation with a fresh key. Repeated unfounded reports can be reviewed for warning/suspension under the existing human-review rule; they are not auto-dismissed.

Every state-changing participant/staff command should use an actor + command + idempotency UUID and canonical request fingerprint, matching the Phase 3 pattern: same key and same input returns the saved safe result; changed input conflicts; a different command has a different key scope. Decision-version, approval, sign-off and execution effects also have unique business identities. Consent binds to its cancellation version; appeal uniqueness is per party and initial decision. A retry never creates another case, approval, appeal, journal or refund operation.

At opening, preserve the exact assignment/allocation, prior work state, accepted terms version and hash, reporter/party role, reason, narrative, requested outcome, follow-up note, server timestamp and authorized relevant conversation references. Do not expose rival applicants' threads. Add later evidence as immutable metadata/references. Each decision version snapshots the exact terms reference/hash, prior work state, amount split, user-facing reason, evidence IDs/content hashes and relevant message IDs/sequences used. New evidence does not rewrite an older decision snapshot. Approval and senior sign-off records bind to that exact decision hash/version.

All outcomes conserve the one allocation's gross principal `P`; kobo arithmetic uses the settled 500 bps half-up rule.

| Outcome     | Worker / commission                                                                                                        | Poster refund               | Assignment / hold                                                                                                                                                                                                                                                                                                           |
| ----------- | -------------------------------------------------------------------------------------------------------------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Full award  | Worker receives `P - round_half_up(P × 500 / 10000)` as internal available earnings; commission is the remainder.          | Zero.                       | Assignment completes; active hold is resolved only at eligible manual finalization. No bank payout is made by case finalization.                                                                                                                                                                                            |
| Full refund | Zero worker award and zero commission.                                                                                     | `P` becomes refund payable. | Assignment is cancelled; payable remains visible through settlement.                                                                                                                                                                                                                                                        |
| Split       | For awarded gross `A`, worker receives `A - commission(A)`, commission applies only to `A`, and refund payable is `P - A`. | Exact remainder.            | Assignment completes for a positive worker award; no refunded gross is charged commission.                                                                                                                                                                                                                                  |
| No action   | No award and no commission.                                                                                                | Zero.                       | After the appeal/finalization gate, restore the prior valid work stage and append a balanced internal reclassification from `job_principal_dispute_held` to `job_principal_assigned`. If the prior state was `submitted`, ordinary poster confirmation becomes available again; it remains a separate poster authorization. |

Every admin disposition, including no action, uses the same immutable decision/evidence snapshot and approved two-person model. Step 5 records proposals and approvals only. Appeal protection and explicit manual finalization remain later gates. No proposal or approval releases earnings, removes a hold, creates a refund payable, or starts an external payment.

## Bounded inputs, evidence and privacy

Use the existing Phase 3 report bounds: reason is one of six controlled values; narrative is 1–2,000 characters; desired outcome is 1–500 characters. Proposed configurable engineering defaults for new free text: optional follow-up detail up to 500 characters, staff contact outcome up to 500, internal note up to 2,000, and appeal/review statement up to 2,000. Never request OTPs, bank details, credentials or raw identity numbers in a case narrative.

The technical source's dispute-file defaults are **up to five files per case, 5,000,000 bytes each**, configurable engineering limits. They are separate from the already approved identity-file rule of **up to three files per verification submission, 5,000,000 bytes each**. Use a case-specific upload/download permission and audit trail; identity-review grants do not grant case-file access. Until an approved scanner/sanitizer can make files safe, actual uploads stay quarantined and unavailable to reviewers; synthetic ready metadata is test-only. No public URL, arbitrary browser object key, unsafe file, unrelated thread, private staff note, third-party identity document or reviewer grant metadata appears in participant responses.

Participant responses are allow-listed: their case/assignment reference, the same shared stage and timeline for both parties, sanitized summaries of each party's relevant case statement, safe requests for information, user-facing decision/reason/amount, appeal eligibility/deadline and truthful refund status. Evidence needed to answer a claim must be shared in a safe/redacted form; raw third-party identity material and unsafe file bytes remain restricted. Do not return internal contact notes, staff grants/IDs, other cases or unrelated conversations. The assigned reviewer may inspect only the relevant terms, case submissions, approved evidence and authorized thread context. Accessing file bytes is a separate scoped, audited check. Financial inspection alone grants no case visibility or authority.

Staff queues should return only bounded triage fields (case/assignment reference, stage, age, reason category and assigned reviewer). A case detail response requires an active staff account, AAL2, the current case-specific grant and current case assignment. Financial approvers see only the immutable decision/evidence references needed to approve that version; raw evidence bytes and unrelated thread content require separate case access. `financial_inspect` may trace safe money references but cannot read the case narrative, evidence or staff notes.

Suspension removes ordinary marketplace writes and money movement. To honor the existing support route for unresolved financial matters, **recommend** permitting a suspended assignment party to open a case on their own eligible funded assignment and then read/respond, submit evidence, appeal once and receive status for that case only. Do not restore browse/apply/post/start/submit/confirm/cancel/withdraw, ordinary chat, staff actions or any money authority. An unverified/non-party or guessed assignment receives the same safe denial/not-found behavior.

## Notifications, appeal clock and refund progress

Persist the same initial decision version and a durable in-app notice for each party in the decision transaction. The 72-hour deadline starts from durable notice to **both** parties: use the later of the two committed notice timestamps plus 72 hours. If either durable notice cannot be committed, do not start the clock or make the decision eligible for finalization. Email is supplementary; failure, opening or delay cannot reset the in-app notice or deadline. Notify both parties durably of a final appeal decision and its written reason. Record server receipt time; an appeal is timely only when received **strictly before** the stored deadline. Equality is late. A client timestamp is never authority.

Each party can appeal once against the initial decision. If both submit before the deadline, preserve both requests and give both to the appeal reviewer; the first request does not consume the other's right. The appeal reviewer must be different from the initial reviewer. An appeal freezes the entire still-unresolved allocation, including any refund portion. A changed outcome creates a new decision version and requires fresh approvals; the initial 72-hour window is not silently reset and there is no second appeal per party. Finalization must account for every appeal receipt that was server-received in time, even if review is still pending. A timer may mark review/finalization eligibility only.

For the deadline race, record an immutable server-side appeal receipt before any longer review work. Finalization must lock the same case/allocation and refuse while any timely receipt remains unresolved. A request received before the deadline cannot lose because its transaction waited for a lock until after it. Keep a test-only historical clock isolated from production commands.

Keep case decision/execution/closure separate from external refund settlement. Proposed behavior: after all appeals are resolved and the authorized decision is manually executed, close the adjudication case while the poster's refund remains visible in its own progress record: `payable` means authorized but not sent; `queued_for_liquidity` means waiting for cleared platform funds/fee coverage; `processing` means the saved provider operation is in flight; `unknown` means it may have been accepted but no authoritative result exists; `failed` or `exception` means ops follow-up is required and the entitlement remains visible; `settled` means authoritative settlement is confirmed. Do not show `settled` from mere provider acceptance. A pending/unknown/failed refund stays actionable for ops and visible to the poster; it is not a spendable balance or a reason to hide unresolved money. Case closure never claims the refund reached a bank account.

Refunds can arise only from an explicit eligible cancellation or a manually finalized full/split outcome. Before any external call, persist one durable operation mapped to the source collection and allocation, exact principal, stable provider reference/idempotency identity, fee treatment and unique business effect. Cumulative authorized/reserved/successful refunds may not exceed the collected charge across slots. Lookup the original operation before retry; unknown cannot be resent with a new identity. Failure preserves the user's refund entitlement and triggers review rather than duplicate wallet credit. Fees are platform expenses; the poster receives the authorized principal. The local fake may prove only its own normalized simulator behavior. Bachs refund support is unresolved; no Bachs request or receipt is claimed.

## Step 4 implemented — local investigation only

Step 4 adds an assigned-reviewer workflow for triage, manual contact logs, targeted information/evidence requests, fact notes, private staff notes and non-response assessment/signoff. It does not add a case outcome, money command, appeal command or finalization path.

Every staff action requires the currently assigned reviewer, an active account, the current `dispute_review` grant and AAL2. Assignment parties cannot investigate or sign off their own case. A participant may answer only an open request addressed to their role; active or suspended parties can use this narrow case-support path at AAL1. Each state-changing action uses actor-scoped idempotency and increments the case version. Database checks are authoritative; the Edge handler rejects extra fields and derives the actor and assurance level from verified Auth.

Safety reason cases are placed first in the reviewer queue and forced to urgent triage priority. Staff may also set other cases urgent. This changes review order only and does not determine an outcome or amount. Contact attempts store channel, result, staff actor, server time and the fixed `simulated_manual_log` attribution. They are manual records only and do not establish that a real call, email or visit happened. Non-response may be assessed only after two recorded no-response attempts across two channels, with substantive reasoning; a separate active `case_senior_signoff` grant, AAL2, a different non-party person and separate reasoning are required to sign that exact contact snapshot. A later contact attempt invalidates the old signoff snapshot.

Information requests use a case-local sequence number rather than a database request ID in participant responses. Requests go only to the named party and create a durable in-app notice. Participant replies and uploaded-file metadata remain private to that participant and the assigned reviewer; the other party receives only their own requests and replies. Reviewer detail includes the accepted terms, only this assignment's captured conversation, triage, contact records, requests/replies, fact findings, private notes, non-response history and file metadata. Shared responses omit staff IDs, private notes, storage keys, hashes, public links and file bytes.

Case files use a private `case-evidence-quarantine` bucket, separate from identity evidence and its reviewer grants. `case_file_policy` defaults to five files per case and 5,000,000 bytes each; these are configurable engineering defaults. The storage/code ceiling is 25 files and 100,000,000 bytes per file if an owner later changes the policy. Identity evidence remains limited to three files. Uploaded bytes pass the existing type/signature checks, then remain `quarantined`; those checks are not a malware scan and never make a file reviewable. There is no promotion command. Only explicitly marked `synthetic_test` metadata may be `ready`, and the local positive byte-download test uses a separately marked synthetic file. A reviewer still needs a current assignment and AAL2 for each byte download; participants cannot fetch quarantined bytes.

The complete participant or reviewer case overview is returned by `case-read`. Each read has its own case and file-metadata audit; byte downloads use a separate authorization and access-audit command. Upload intents are short-lived and idempotent, and clients receive no public Storage URL. Actual upload failures leave no reviewable evidence. An interrupted upload can leave an object without finalized metadata; until a reviewed scanner/cleanup policy exists, keep it private and quarantined and do not infer a retention period.

### Step 2 implementation — 6 November 2026

Migration `20261106000100_assignment_cases_and_scoped_timeline.sql` adds a separate current case lifecycle. It preserves immutable `assignment_holds` reports and backfills existing reports into active case records. The new partial unique index allows at most one active case per allocation; a closed historical case can later coexist with a new current case. No case-closing, decision, appeal, cancellation or refund command is exposed in this step.

The implemented lifecycle currently supports `open → under_review` through explicit reviewer assignment. An unassigned reviewer may take a case only for themselves with an active account, current `dispute_review` grant and AAL2; only the current assigned reviewer can transfer it. Reviewers cannot be either assignment party. A reviewer queue contains only case/assignment references, stage, age and reason category. Detailed staff reads require the current case assignment and are audited; financial inspection alone grants no case access.

Participants read the same shared stage and allow-listed timeline. Staff assignment updates do not expose the reviewer identity. Reviewer detail is limited to the accepted terms hash/version and the accepted assignment's own conversation through the message sequence recorded when the case opened. Rival application threads, private staff assignment metadata and third-party identity files are not included. Suspended participants may open and read only their own eligible funded assignment case; this does not restore ordinary marketplace actions.

The case file policy row has configurable engineering defaults of five files and 5,000,000 bytes per file, separate from identity verification's three-file limit. No case file upload/download path is implemented here; uploaded evidence remains gated by the documented scanning/quarantine requirements.

The allocation remains the financial source of truth: an active case and `dispute_held` allocation must agree at the database boundary. Wallet held totals and reconciliation continue reading allocation/journal state rather than report rows, so an immutable historical report cannot keep a resolved case held. `confirm_completion_for_actor()` now checks effective active-case state and no longer checks for any historical report. Start and submit continue to deny on the canonical held allocation state. No release or journal correction occurs in Step 2.

### Step 3 implementation — voluntary cancellation and refund authorization

Migration `20261106000200_assignment_cancellations.sql` and the four new `marketplace-command` actions implement voluntary cancellation only. `cancel_unassigned_slots` checks every selected allocation separately for the owning active poster and current `can_hire`; each eligible, still-unassigned slot becomes a distinct exact-gross refund payable. Ineligible entries return their own result while eligible entries in the same request can proceed. Acceptance and cancellation lock the same job/allocation state, so the slot is either assigned to a worker or becomes payable, never both. A batch retry returns the saved per-slot response; changing its contents under the same key conflicts.

For an accepted assignment, `request_prestart_cancellation` records the requester's consent against one immutable assignment, accepted terms version/hash and cancellation version. It does not move money or block work-start. The other party's explicit matching consent is the only action that can finalize it; final consent and work-start serialize on the same allocation. If work starts first, consent is stale. If consent wins first, the assignment closes and the same gross principal becomes one refund payable. A normal poster confirmation is not routed through a case.

`abandon_prestart_assignment` is worker-only and works only while the assignment has not started and has no active case. It closes that assignment and application, makes the original thread read-only, and returns the still-held allocation to discovery only if the original deadline has not passed. It creates no refund payable or poster charge. `allocation_assignment_bindings` keeps every prior assignment link while permitting only one current binding, so a reused allocation cannot later be released by an old assignment. Terms and the original application/thread remain historical records.

The wallet adds an owner-only, kobo-string `poster_refund_payable_kobo` total and up to 20 safe `authorized` payable summaries. Step 3 does not add refund progress beyond authorization, a provider refund operation, runner path or external settlement. No timer, silence, reminder or deadline triggers cancellation or money movement. Case decision/appeal routes remain separate from these participant-authorized actions.

The local SQL and actual Edge acceptance journeys exercise per-slot mixed results, unauthorized/suspended attempts, start-versus-abandonment, start-versus-final-consent, acceptance-versus-unused-slot cancellation, duplicate consent replay, exact payable/journal counts, historical binding reuse, wallet projection and unchanged case count. All payment fixtures use the local simulator for collection only; they do not simulate or claim a refund settlement.

### Step 5 implemented — decision proposals and approvals only

Migration `20261106000400_case_decisions_and_approvals.sql` adds immutable decision versions, financial approvals and separate decision non-response sign-offs. A current assigned reviewer with active `dispute_review` and `financial_approve`, AAL2, an active account and a trusted human principal may propose. The proposer cannot be either case party. The proposal records the first financial approval; a different current qualified human with `financial_approve` and AAL2 supplies the second. Approval identity is checked independently of role grants, so one person with multiple grants still counts as one person. `financial_inspect` remains read-only.

Each version binds the outcome, exact gross award/refund, derived recipients, required 5% half-up commission on awarded gross only, user-facing reason, terms and evidence snapshot, snapshot hash and decision hash. ### Step 6 implemented — durable decision notice and appeal review

Migration `20261106000500_case_decision_notifications_and_appeals.sql` publishes an approved initial decision by writing one shared decision event, one in-app notice to each party and one immutable publication record in the same transaction. Both notices carry the same decision version and durable timestamp. The stored appeal deadline is exactly 72 hours later. Email is supplementary; opening a notice or sending email does not change the stored time. A changed appeal outcome sends both parties a safe result notice but does not restart this initial clock.

Each participant may file once, strictly before the stored deadline. The receipt RPC records server time in a committed row before a separate processing RPC locks the case. The request has no client timestamp field. The one-per-party rule preserves both worker and poster appeals, and the read projection returns only the caller's own statement plus a boolean indicating whether the other party also appealed. A late appeal receives a support route and is not recorded as timely. Private gate checks block finalization while the initial window is open, a timely appeal is unresolved or an appeal evidence request remains open. This step does not expose a finalizer.

An appeal reviewer is a current human staff account with AAL2, case scope and active `case_appeal_review`, `dispute_review` and `financial_approve` grants. The reviewer cannot be a case party or the initial reviewer. The scoped reviewer may request more information/evidence, then record an immutable `upheld` or `changed` review version with its decision/evidence snapshot. Participants can answer their own open request at AAL1; suspended parties retain this same narrow case-support route. Actual uploaded files stay quarantined. A changed outcome must select a later independently approved decision version; it cannot reuse approvals from an earlier version, and any required non-response sign-off must match that version. Proposing or reviewing an appeal never releases or refunds money.
