## Phase 5 Step 3 implementation and evidence — 11 November 2026

- Added `20261110000200_private_realtime_invalidation.sql`. Database triggers publish only `{"kind":"invalidate"}` for application message/read changes, notice creation/first-read changes and case timeline changes. Payloads contain no message, notice, case, identity or money fields. The client also removes the Realtime transport message ID before forwarding a hint to application code.
- Topic issuance is through the `realtime-topic` Edge Function. It verifies the bearer token with local Supabase Auth, checks the token subject matches the verified user, derives AAL from the signed token and calls a service-only RPC. Callers cannot select another actor or pass an AAL claim. Topics are private and include actor ID plus authorization generation. Current `realtime.messages` SELECT RLS checks actor, generation and current thread, notice or case access; there is no client Broadcast INSERT policy. The local Realtime tenant was set to and verified in private-only mode through its local management API.
- Authorization generation advances when account status/capability/staff grants and relevant identity bindings change, and when case reviewer assignment changes. A rotated generation prevents future publisher events from targeting the old topic. Durable thread and notice reads still use their current command/database authorization checks.
- The pinned local native stack used Supabase CLI 2.122.0, `@supabase/supabase-js` 2.118.0 and local Realtime runtime `v2.147.1-r0`. The test used two Auth-backed participant clients and an Auth-backed AAL2 reviewer client over `127.0.0.1:54321/realtime/v1/websocket`.
- The local journey passed private participant joins; denial of public, unrelated-applicant, wrong-party and cross-user-notice joins; denial of client message/read hint writes; actor-scoped message, read-cursor, notice-creation and first-notice-read invalidations; and logout channel cleanup. Repeating the same notice-read command did not emit another hint. The assigned AAL2 reviewer joined its case topic, while AAL1, unassigned-reviewer and reviewer-to-participant-thread joins were denied. After suspension, the already-connected applicant socket stayed open without receiving later protected hints, a new join to its stale topic failed, and the same user’s authoritative thread read, send and cursor commands were denied. Restoring eligibility issued a new topic; replay recovered the message saved while suspended and live delivery resumed.
- The participant replay subscribed before reading durable history, injected a message during the first page, reconciled the race, and deduplicated the overlapping hint/replay by server sequence. Thread sequences remained decimal strings. Notice and thread state are recovered through durable reads, not through the hint payload.
- Warm local loopback saved-to-received samples were **9, 6 and 12 ms**. The test subtracts the saved message's database `created_at` from the local Node client's receive time. This is a three-sample, same-host timing check; it does not represent Nigerian mobile networks or production load.
- `node --test tests/unit/realtime/*.test.mjs` passed 5/5 tests. `npm run check:database` passed all 18 SQL test files and 1,016 pgTAP assertions, removed the marked synthetic Auth fixtures, confirmed generated public database types were current, and stopped Supabase. `npm run typecheck:edge`, `npm run lint`, `npm run typecheck` using the repository's pinned Node 22 runtime, and targeted Prettier checks passed.
- The focused native journey, `NBD_REALTIME_CASE_ONLY=1 node scripts/check-marketplace-local.mjs`, passed through the assigned-reviewer Realtime check, then cleared synthetic data and stopped Supabase.

### Runtime and revocation limits

Supabase Realtime caches private-topic authorization for connected channels. The tested generation strategy suppresses future hints to the old topic and denies new joins after suspension or reassignment; it does not force the existing WebSocket to disconnect. A hint already dispatched or in flight at the exact instant authorization changes cannot be recalled. This local journey checked delivery after the suspension transaction committed, not a send-versus-suspension race at the same instant. Consumers must treat hints only as prompts to fetch current authorized state. No production endpoint, hosted runtime, representative device, load test or real Nigerian network was used; those checks remain for Phase 6.

## Phase 5 Step 5 implementation and verification status — 11 November 2026

- Migration `20261111000200_assignment_submission_reminders.sql` creates one durable due row per submitted assignment, accepted-terms version, source-generation event and stage. Normal sequences anchor to the committed `submitted_at`; an approved no-action finalization creates a fresh generation only when it restores `submitted` and anchors it to the finalization server time.
- The owner-approved recipients are enforced at insert: the poster receives the 24/48-hour action reminders and the worker receives 72-hour dispute-route guidance. Each key binds assignment, terms version, generation event and stage. Claims use a 60-second lease, at most five attempts, bounded retry delay and expired-lease reclaim. Catch-up selects only the latest due stage and coalesces older due stages once.
- Dispatch locks the assignment row, then rechecks submitted state, assigned allocation and absence of an open case before committing a notice. Completion, cancellation, dispute and superseding sequence events suppress pending schedule rows and email intents. This lock order serializes dispatch against completion/dispute commands without holding the allocation row and avoids the case-finalization lock order.
- A successful dispatch transaction appends a safe marketplace event, the recipient-only in-app notice and its existing Step 4 email intent. The schedule worker has no provider adapter. The email consumer rechecks reminder eligibility just before its send call; an outbound request already in flight cannot be recalled.
- `assignment-reminder-runner` is a server-secret-gated, empty-POST Edge route. It is disabled by default and processes at most 25 reminders per invocation. It calls only reminder claim/dispatch/retry RPCs. It has no public client-time parameter and does not invoke an earnings, payout, refund or case command. A hosted cron schedule has not been provisioned.
- Database boundary tests were added to `014_marketplace_applications.test.sql` for due/not-due, duplicate claim, lease expiry/reclaim, bounded retry, 24/48 recipients, claimed-reminder suppression after dispute, no-action rescheduling, 80-hour catch-up, worker guidance and unchanged journal/allocation/case/balance state. ## Phase 5 Step 6 implementation and verification status — 11 November 2026
